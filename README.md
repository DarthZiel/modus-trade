# Modus Feedback

Production на одном VPS Basic-2: [deploy/README.md](deploy/README.md),
отдельный `compose.production.yaml`, Caddy/HTTPS и архивы релизов.

Лендинг команды Iron Tech для `iron-tech.kz` находится отдельно в `landing/`.
Запуск: `cd landing && npm ci && npm run dev`; подробности —
[landing/README.md](landing/README.md). Сервис обратной связи остаётся в
`frontend/` и готовится к размещению на `feedback.iron-tech.kz`.

MVP системы обратной связи сотрудников «Модус Трейд».
Требования и границы проекта: [MVP_SPEC.md](MVP_SPEC.md).

## Быстрый запуск

Нужны Docker Engine и Docker Compose v2. Из корня проекта:

```bash
cp .env.example .env
docker compose up --build -d
```

Команда запускает PostgreSQL, применяет миграции и поднимает API и сайт.
Telegram-токен и ключ ИИ не нужны.

- Сайт: http://localhost:5173
- API и проверка БД: http://localhost:8000/health
- Swagger: http://localhost:8000/docs
- API через сайт: http://localhost:5173/api/health

Порты можно изменить через `WEB_PORT` и `API_PORT` в `.env`.
Доступ привязан к локальному компьютеру. Это конфигурация для разработки,
для публикации потребуются HTTPS и отдельные настройки окружения.

```bash
docker compose logs -f
docker compose down
```

База сохраняется в Docker volume после остановки. `docker compose down -v`
удаляет локальные данные без возможности восстановления.

## Структура

- `backend/` — FastAPI, SQLModel, PostgreSQL и Alembic.
- `frontend/` — React + TypeScript + Vite; общая основа сайта и Mini App.
- `bot/` — aiogram; отдельный необязательный сервис.
- `compose.yaml` — локальная инфраструктура.

## Telegram-бот

Создайте бота через BotFather и укажите `BOT_TOKEN` в `.env`, затем:

```bash
docker compose --profile bot up --build -d
```

Пока реализована только команда `/start`. Подача обращений, приглашения,
авторизация Telegram Mini App и ИИ появятся в следующих задачах.
Локальный сайт пока не является подключённым Mini App: для этого также
потребуется публичный HTTPS-адрес и настройка бота.

## Разработка без пересборки Docker

Нужны Python 3.12+, uv и Node.js 22.12+.
Базу и backend можно оставить в Docker, а frontend запускать отдельно:

```bash
docker compose up --build -d db backend
cd frontend
npm ci
npm run dev
```

Vite проксирует `/api` на `http://localhost:8000`. При изменении API_PORT
обновите адрес в `frontend/vite.config.ts`.

Для backend из каталога `backend`:

```bash
uv sync --frozen
uv run alembic upgrade head
uv run fastapi dev
```

При таком запуске укажите `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`,
`DB_NAME` в корневом `.env`; локальные значения по умолчанию заданы в
`backend/app/config.py`. PostgreSQL в Compose не публикует порт наружу:
для backend вне Docker нужен отдельно доступный PostgreSQL.

## Миграции

```bash
docker compose exec backend alembic current
docker compose exec backend alembic revision --autogenerate -m "description"
docker compose exec backend alembic upgrade head
```

При создании миграции внутри контейнера скопируйте её в исходники:
`docker compose cp backend:/app/alembic/versions/. backend/alembic/versions/`.
Модели таблиц нужно импортировать в `backend/alembic/env.py`.
Начальная миграция `0001` создаёт только основу истории Alembic;
миграция `e118b7425487` добавляет компании, подразделения, пользователей,
приглашения и сессии.

```bash
cd frontend
```

## Пользователи и приглашения

После `docker compose up --build -d` создайте первого координатора:

```bash
docker compose exec backend python -m app.bootstrap --email your-email@example.com --name "Ваше имя"
```

Команда интерактивно запросит пароль (12–128 символов) и его повторение.
Пароль не передаётся аргументом командной строки. При необходимости задайте
`--company "Название" --department "Подразделение"`.
Готовых паролей и публичной регистрации в приложении нет.

1. Войдите на сайт с созданными email и паролем.
2. Во вкладке «Структура компании» добавьте нужные компании и подразделения.
3. Создайте приглашение: имя, email, компания, подразделение, дополнительные
   роли и срок действия (1, 7 или 30 дней).
4. Скопируйте ссылку и передайте сотруднику. Она показывается только один раз;
   потерянное приглашение нужно отозвать и создать заново.
5. Сотрудник откроет ссылку, задаст пароль и войдёт в свой кабинет.

Каждый пользователь имеет роль сотрудника; роли ответственного и координатора
можно добавлять одновременно. Координатор управляет командой. После блокировки
пользователя его сессии удаляются. Последнего активного координатора отключить
или лишить роли нельзя.

Приглашение одноразовое; срок действия и отзыв проверяются сервером.
В БД хранятся только хеши приглашений и сессий, пароли хешируются Argon2.
Сессия действует 7 дней, cookie — HttpOnly / SameSite=Lax. Для HTTPS установите
`COOKIE_SECURE=true` и пересоздайте backend. В изменяющих запросах API нужен
заголовок `X-Modus-Request: 1` (включая вход и предварительный просмотр приглашения).
Он автоматически добавляется веб-клиентом. CORS не разрешён.
Ограничение попыток входа хранится в памяти одного процесса; при масштабировании
его нужно перенести в общее хранилище. Очистка истёкших записей сессий,
восстановление пароля и привязка Telegram будут отдельными задачами.

Ссылки приглашений содержат секрет во фрагменте URL; веб-клиент убирает его из
адресной строки после чтения. Для активации после перезагрузки страницы откройте
исходную ссылку повторно. Ссылки и пароли не следует публиковать.

### Интеграционные проверки аккаунтов

Тесты работают только в отдельной PostgreSQL-базе с именем, оканчивающимся на
`_test`, и удаляют её предметные данные перед каждым сценарием.
Создайте её один раз (замените `modus`, если изменили POSTGRES_USER):

```bash
docker compose exec db psql -U modus -d postgres -c 'CREATE DATABASE modus_test;'
docker compose run --rm -e DB_NAME=modus_test backend uv run --frozen python -m pytest -q tests
```

Тесты сами применяют миграции. Проверяются роли, вход и выход, истечение сессий,
блокировка, одноразовость и конкурентная активация приглашений, отзыв, сроки,
валидация компании/подразделения, защитный заголовок и ограничение попыток входа.


## Подача обращений через сайт

После входа откроется раздел «Мои обращения». У координатора также доступна
вкладка «Управление командой»; свои обращения он подаёт на общих основаниях.

1. Нажмите «Новое обращение» и выберите «Проблема» или «Идея».
2. Укажите заголовок (5–160 символов) и описание (10–10000 символов).
3. Выберите категорию или оставьте «Другое».
4. При необходимости прикрепите до 5 файлов по 10 МБ: JPEG, PNG, WebP или PDF.
5. Проверьте предпросмотр и нажмите «Отправить обращение».
6. Откроется карточка с номером `MT-000001`, статусом «Получено», вложениями
   и записью в истории. Компания, подразделение и автор берутся из профиля.

В списке есть фильтры «Все», «Активные», «Требуют моего ответа», «Завершённые»
и постраничная загрузка. Доступны создание, просмотр, очередь и назначение ответственного. Переписка
и остальные переходы статусов будут реализованы следующим этапом.
Ссылки вида `/appeals/123` можно открывать напрямую, в том числе после входа.

Форма сохраняет введённые данные при ошибке отправки. Повторный запрос с тем же
ключом и содержимым возвращает ранее созданное обращение, включая одновременные
запросы. Черновик хранится только в памяти открытой страницы и теряется при
перезагрузке. После отправки описание не редактируется.

Файлы хранятся в Docker volume `uploads_data`, отдельно от PostgreSQL. При
резервном копировании нужно сохранять оба хранилища. Локальный путь backend
настраивается через `UPLOAD_DIR` (по умолчанию `backend/uploads` при запуске
из каталога backend). Удаление volumes удаляет и вложения.

Изображения проверяются по содержимому, расширению и размеру (до 25 мегапикселей);
для PDF проверяется сигнатура формата. Файлы выдаются как скачивание с проверкой
доступа на каждый запрос. Автор видит свои обращения; координатор имеет доступ
к карточкам всех обращений; ответственный — к назначенным ему. Список
«Мои обращения» для любой роли содержит только собственные записи.

### API обращений

- `POST /appeals` — multipart-форма: `kind` (`problem` / `idea`), `title`,
  `description`, `category`, `submission_id` (UUID), необязательные повторяемые
  части `files`. Заголовок `X-Modus-Request: 1` обязателен.
- `GET /appeals?filter=all&page=1&page_size=20` — собственные обращения.
  Фильтры: `all`, `active`, `needs_reply`, `completed`; размер страницы до 50.
- `GET /appeals/{id}` — карточка и история.
- `GET /appeals/{id}/attachments/{attachment_id}` — скачивание вложения.

Общий предел тела запроса — 52 МиБ, включая multipart-разметку. Он проверяется
и в nginx, и в backend, в том числе для потоковых запросов без Content-Length.
Миграция `6c999ff3885a` добавляет обращения, вложения и события истории.
Интеграционные тесты обращений запускаются той же командой, что и тесты аккаунтов;
файлы тестов сохраняются во временных каталогах отдельно от рабочего volume.


## Очередь координатора и назначение ответственных

Координатор видит вкладку «Очередь обращений», ответственный — «Назначенные мне».
Личный список «Мои обращения» остаётся отдельным и содержит только авторские записи.

В общей очереди доступны поиск по номеру, заголовку, описанию и имени автора,
фильтры по типу, статусу, компании, подразделению и ответственному, а также
выборки «Без ответственного», «Просроченные», «Ожидают подтверждения».
Ответственный получает только свои назначения, независимо от переданных фильтров.

Чтобы распределить обращение:

1. Убедитесь, что нужный активный сотрудник имеет роль «Ответственный»
   (координатор добавляет её в разделе «Управление командой»).
2. Откройте карточку из очереди, выберите ответственного и будущую дату ответа.
   Время вводится в часовом поясе браузера, сервер хранит UTC.
3. Сохраните назначение. Первое назначение переводит «Получено» в «На рассмотрении».
4. Для переназначения или изменения срока укажите причину. Она будет видна
   автору в истории вместе с координатором и временем действия.

Назначение доступно только координатору. Завершённые и отклонённые обращения
перераспределять нельзя. Отключённые сотрудники и сотрудники без роли
ответственного не предлагаются для новых назначений. Если уже назначенный
сотрудник недоступен, в очереди и карточке показывается предупреждение.

При переназначении прежний ответственный теряет доступ, если он одновременно
не автор или координатор. Просрочка считается по дате следующего ответа,
завершённые обращения в неё не входят. Автор может нажать «Обновить карточку»,
чтобы увидеть текущее назначение и срок; автоматические уведомления — отдельный этап.

Одновременное редактирование защищено версией назначения: второй координатор
получает HTTP 409 и должен обновить карточку. Повторное сохранение неизменных
значений с актуальной версией не создаёт событие в истории.

API:

- `GET /work/appeals` — рабочая очередь; фильтры `filter`, `status`, `kind`,
  `company_id`, `department_id`, `responsible_id`, `q`, `page`, `page_size`.
- `GET /work/responsibles` — активные кандидаты для назначения, только координатор.
- `PATCH /work/appeals/{id}/assignment` — `responsible_id`, `next_response_at`
  (ISO 8601 с часовым поясом), `expected_version`, `reason`.

Миграция `7a001` добавляет версию назначения, сохраняя существующие обращения.
Тесты очереди запускаются общей командой `python -m pytest -q tests` в тестовой БД.

## Переписка и рассмотрение

В карточке обращения доступна текстовая переписка автора, координатора и текущего
ответственного. У сообщений сохраняются отправитель и время. Предыдущие сообщения
загружаются порциями по 50; редактирование и удаление сообщений не предусмотрены.
При сетевой ошибке введённый текст сохраняется. Повторная отправка с тем же UUID
не создаёт дубликат. В этой задаче новые вложения в переписке не добавляются;
вложения исходного обращения по-прежнему доступны в карточке.

Ответственный или координатор может:

- принять назначенное обращение в работу: «На рассмотрении» → «В работе»;
- запросить уточнение: вопрос появляется в переписке, статус — «Нужно уточнение»;
- зафиксировать выполнение с обязательным описанием результата;
- отклонить с обязательным объяснением.

Ответ автора на запрос уточнения возвращает статус, который был до запроса:
«На рассмотрении» или «В работе». Сообщение другого участника этого не делает.
Обычная переписка сама по себе не меняет остальные статусы. После отклонения
автор может задать вопрос в переписке, статус остаётся «Отклонено».

Выполнение переводит обращение в «Ожидает подтверждения», а не закрывает его.
Подтверждение автором и возврат в работу доступны в карточке результата. После фиксации выполнения или отклонения срок следующего ответа снимается,
чтобы обращение не числилось просроченным после предоставленного ответа. Результат/причина
отклонения и время фиксации видны отдельным блоком, действия записываются в историю.
Пока ожидается уточнение, зафиксировать решение нельзя — сначала нужен ответ автора.

Версия карточки (`assignment_version`) теперь меняется также при сообщениях и
действиях рассмотрения. Назначение и решение с устаревшей версией отклоняются
HTTP 409; введённое объяснение сохраняется до обновления карточки. Изменения
доступны после нажатия «Обновить карточку» / «Обновить переписку»; автоматические
уведомления будут реализованы отдельно.

API:

- `GET /appeals/{id}/messages?before_id=...` — последние 50 сообщений или предыдущая
  порция; `items` в хронологическом порядке, `has_more` указывает на старые сообщения.
- `POST /appeals/{id}/messages` — `client_id` (UUID) и `body` (1–10000 символов).
- `POST /appeals/{id}/review` — `action` (`start`, `request_info`, `resolve`, `reject`),
  `expected_version`, `explanation` (обязателен кроме `start`).

Миграция `8b001` добавляет переписку и поля решения, сохраняя существующие обращения.
Прогресс крупных задач хранится в `DEVELOPMENT_PROGRESS.md`.


## Подтверждение результата автором

Когда ответственный фиксирует выполнение, автор видит блок «Помогло ли решение?»:

- «Помогло — закрыть»: обращение получает статус «Закрыто»; комментарий необязателен.
- «Проблема осталась»: автор указывает обязательную причину и возвращает обращение.

Возврат активному ответственному переводит обращение в «В работе». Если прежний
ответственный заблокирован, лишён роли или отсутствует, назначение снимается,
статус становится «Получено» и обращение появляется у координатора без ответственного.
Новый срок следующего ответа координатор назначает отдельно — произвольный SLA
система автоматически не создаёт.

Предыдущий результат не теряется: сохраняется снимок результата, оценка, комментарий
и время ответа автора. Возврат также добавляет сообщение в переписку. При повторном
выполнении автор оценивает новый результат. Подтвердить или вернуть обращение может
только его автор, включая случай, когда автор одновременно имеет другие роли.
Координатор и ответственный не могут подтвердить результат за другого сотрудника.
После закрытия переписка сохраняется, но сообщения не открывают обращение заново.

API: `POST /appeals/{id}/feedback` с полями `client_id` (UUID), `outcome`
(`helped` / `reopen`), `comment` (до 10000 символов), `expected_version`.
Для `reopen` непустой комментарий обязателен. Оценка доступна только в статусе
`awaiting_confirmation`; версия защищает от устаревшей карточки. Повтор того же
запроса возвращает текущее обращение без повторного действия, даже если после
возврата уже начался следующий цикл рассмотрения. Изменение ответа с тем же
ключом возвращает HTTP 409.

Миграция `9c001` добавляет журнал оценок автора. Права, повторные запросы,
возврат при недоступном ответственном и конкурентные ответы проверяются в
`backend/tests/test_feedback.py` общей командой тестов на отдельной тестовой БД.

### Уведомления и напоминания

В шапке кабинета доступен центр уведомлений: счётчик непрочитанных, переход в
обращение, чтение одного или всех уведомлений, страницы по 20 записей. Список
обновляется каждые 30 секунд и при возврате в окно. При переходе уведомление
отмечается прочитанным. Доступ проверяется заново: после переназначения прежний
ответственный не видит уведомления по чужому обращению.

События сохраняются в PostgreSQL в одной транзакции с действием: приём обращения,
назначение и перенос срока, сообщение, запрос уточнения, начало работы, результат,
отклонение, подтверждение или возврат автором. Собственные действия не создают
уведомлений исполнителю (кроме квитанции о подаче). Автор и текущий ответственный
получают изменения; если ответственного нет или он недоступен, уведомляется
координатор. При переносе срока новая дата и объяснение доступны в карточке.

Сервис `reminders` запускается обычным `docker compose up --build -d` и проверяет
сроки раз в минуту:

- при просрочке — одно напоминание ответственному и координаторам;
- через 3 дня ожидания подтверждения — одно напоминание автору;
- после переноса срока или нового результата допускается новое напоминание;
- закрытые и отклонённые обращения не создают напоминания; автоматического
  закрытия при молчании автора нет.

Уникальный ключ в БД предотвращает дубликаты при перезапусках и параллельных
проверках. Ошибка проверки записывается в лог; процесс повторяет её через минуту.
Проверка: `docker compose logs --tail=30 reminders`.

API: `GET /notifications?page=1`, `POST /notifications/{id}/read`,
`POST /notifications/read-all`. Нужны сессия и защитный заголовок для POST.
На этом этапе работает веб-доставка; Telegram подключается на следующем этапе.

### Telegram-бот и Mini App

Подготовлены привязка аккаунта из кабинета, вход Mini App по подписанным данным
Telegram, подача через диалог с вложениями, список и карточка, ответы и оценка
результата, доставка уведомлений. Без настроенного бота сайт работает полностью;
раздел **Telegram** показывает состояние подключения.

Настройка BotFather, HTTPS, переменных окружения, запуск и контрольный сценарий:
[TELEGRAM_SETUP.md](TELEGRAM_SETUP.md). Токен бота и отдельный BOT_API_SECRET
хранятся только в `.env`. Профиль `bot` по умолчанию не запускается.

### ИИ-помощник и эксперименты

В форме обращения и в боте доступна помощь с формулировкой: отдельное предложение,
до двух уточнений и явное применение. Исходный текст сохраняется в карточке.
Настройка модели и отличие деморежима: [AI_SETUP.md](AI_SETUP.md).

В карточке ответственный или координатор может утвердить план эксперимента,
срок и критерий успеха, записать исходное измерение, завершить проверку с итогом
«Внедрить шире / Доработать / Прекратить». Автор оставляет свой комментарий.
Без пары численных измерений система явно показывает, что количественный эффект
не подтверждён. Разность до/после не выдаётся за доказательство причинности.

До завершения активного эксперимента нельзя зафиксировать закрывающее решение
по обращению. При смене ответственного активная проверка передаётся новому
исполнителю. Истечение срока вызывает одно напоминание; автоматического завершения
нет. Обзор очереди показывает активные эксперименты и подтверждённые результаты.

Локальный сценарий для жюри и демонстрационные аккаунты: [DEMO_GUIDE.md](DEMO_GUIDE.md).

OpenRouter поддерживается отдельным адаптером: `AI_PROVIDER=openrouter`, ключ
`OPENROUTER_API_KEY`, ID `OPENROUTER_MODEL`; отдельная модель плана задаётся
через `OPENROUTER_EXPERIMENT_MODEL`. Режимы `schema`, `json`, `prompt` описаны
в [AI_SETUP.md](AI_SETUP.md). Модели меняются через .env без изменения кода.

### Дизайн интерфейса

Самостоятельная айдентика «Модус Трейд · Фидбек» описана в `DESIGN.md`,
контекст сервиса — в `PRODUCT.md`. Компоненты shadcn/ui хранятся исходным кодом
в `frontend/src/components/ui`; Tailwind v4 подключён через Vite. Golos Text
с кириллицей загружается локально. Навыки shadcn и Impeccable установлены
в `.agents/skills`, расширенные токены — в `.impeccable/design.json`.

Если `npm run dev` сообщает о лимите файловых наблюдателей `ENOSPC`, локально
запускайте `CHOKIDAR_USEPOLLING=true npm run dev`. Production-сборке polling не нужен.
