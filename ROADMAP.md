# План развития: 100 пользователей в день

Цель — перейти от пилота хакатона к ежедневной работе: **100 активных
сотрудников в день** во всех каналах (сайт, Mini App, бот). Ниже расчёт
нагрузки, что выдержит текущая архитектура, что сломается первым, и план
по этапам.

## 1. Сколько это нагрузки

Оценка на 100 активных пользователей в день (≈ 300–500 сотрудников в базе):

| Показатель | Оценка в день | Пик |
| --- | --- | --- |
| Новые обращения | 20–40 | 5–8 в час в начале смены |
| Сообщения, оценки, действия | 200–400 | — |
| Открытые вкладки, опрос уведомлений раз в 30 с | до 100 вкладок × 120 запросов/ч | ≈ 3–5 запросов/с |
| Поиск похожих при наборе (раз в 0,65 с паузы) | 100–300 поисков | < 1 запроса/с |
| Вызовы ИИ (формулировка, черновики, голос) | 30–80 | 5–10 в час |
| Вложения | 10–20 файлов, 30–100 МБ | — |

**Вывод:** по запросам это небольшая нагрузка. Текущий VPS (2 vCPU, 2 ГБ RAM,
один процесс Uvicorn, PostgreSQL 17) выдерживает её с большим запасом:
типичный запрос API — единицы миллисекунд, а поиск похожих по триграммам
по нескольким тысячам обращений — десятки миллисекунд.

Что действительно станет узким местом при 100 пользователях в день —
**не процессор, а процессы, надёжность и люди**:

1. Координатор не успеет вручную распределять 30–40 обращений в день.
2. Один сервер без мониторинга: сбой ночью заметят только утром.
3. Резервные копии лежат на том же сервере.
4. Диск: вложения растут на 1–3 ГБ в месяц, а свободно около 30 ГБ.
5. Ограничение частоты запросов хранится в памяти одного процесса:
   при переходе на несколько процессов его нужно вынести в Redis или PostgreSQL.

## 2. Этапы

### Этап 0. Готовность к ежедневной работе — 1–2 недели

Цель: сервис не падает незаметно, данные нельзя потерять.

- **Мониторинг и оповещения:** внешняя проверка `/api/health` раз в минуту
  (UptimeRobot или Healthchecks) с уведомлением в Telegram дежурному.
- **Ошибки:** Sentry (или self-hosted GlitchTip) для backend, бота и фронтенда.
- **Резервные копии вне сервера:** ежедневный `deploy/backup.sh` → объектное
  хранилище (S3-совместимое), хранение 30 дней, **ежемесячная проверка
  восстановления** на отдельной машине.
- **CI в GitHub Actions:** тесты backend и бота, `tsc` и сборка фронтенда
  на каждый PR; сборка образов с тегом коммита.
- **Стейджинг:** копия стека на том же или отдельном VPS для проверки
  релизов и миграций до прода.
- **Безопасность:** вход по SSH только по ключу (сделано), firewall
  (только 22/80/443), автоматические обновления безопасности Ubuntu,
  второй фактор для координаторов.

### Этап 1. Процессы под поток — 1-й месяц

Цель: 30–40 обращений в день разбираются без перегруза координатора.

- **Автоназначение по правилам:** категория + подразделение → ответственный
  и срок по умолчанию; координатор только проверяет исключения.
- **Сроки по категориям (SLA):** например, «Условия труда» — ответ за 1 день,
  «Процессы» — за 3 дня; просрочки видны на «Эффекте».
- **Ежедневная сводка** координатору и ответственным в Telegram: новое,
  просроченное, ждёт подтверждения автора.
- **Объединение дублей координатором:** если сотрудник всё же создал дубль,
  координатор переносит его автора в «присоединившиеся» к основному обращению.
- **Массовое подключение сотрудников:** импорт списка из CSV, QR-коды
  на постерах в складах для привязки бота.
- **Метрики внедрения:** активные пользователи в день, доля обращений через
  бот, голос и сайт; время до первого ответа по подразделениям.

### Этап 2. Масштаб и качество — 2–3 месяц

Цель: запас по мощности ×10 и лучшее качество подсказок.

- **Сервер:** 4 vCPU / 8 ГБ RAM или управляемый PostgreSQL. Два-три процесса
  Uvicorn; лимиты частоты и блокировки — в Redis.
- **Файлы:** вложения в объектное хранилище вместо диска сервера;
  загрузка по подписанным ссылкам.
- **Семантический поиск похожих:** эмбеддинги (`pgvector`) поверх триграмм,
  чтобы находить совпадения по смыслу («нет света у стола» ≈ «плохо видно
  маркировку»).
- **Фоновые задачи:** отдельная очередь для ИИ и голоса с повторами,
  чтобы медленный провайдер не задерживал запросы.
- **Единый вход:** SSO / корпоративный каталог вместо приглашений по одному.
- **Журнал аудита** для проверок: кто, что и когда изменил, с выгрузкой.

### Этап 3. Развитие продукта — после 3 месяцев

- Публичная для компании витрина «Что мы изменили по вашим обращениям»
  (только подтверждённые результаты, без авторов).
- Связанные эксперименты в разных подразделениях: «внедрить шире» одним действием.
- Интеграции с учётной системой (1С) для автоматических измерений «до/после».

## 3. Юридические и организационные вопросы

- **Персональные данные:** обращения именные. Нужно согласовать
  с юристами компании место хранения данных (требования о локализации
  персональных данных граждан РФ, 152-ФЗ) и, при необходимости, перенести
  сервер в соответствующий дата-центр.
- **Внешний ИИ:** тексты передаются провайдеру только после явного согласия,
  без имён и профилей. Для масштабирования рассмотреть провайдера с хранением
  данных в нужной юрисдикции или локальную модель.
- **Роли:** назначить владельца продукта, дежурного администратора и
  ответственных по категориям; утвердить сроки ответа.
