## Состав

| Номер | Этап | Что показать |
| --- | --- | --- |
| MT-000001 | Получено | Назначение ответственного и первого срока |
| MT-000002 | Получено | Собственная идея координатора об инструкциях |
| MT-000003 | На рассмотрении | Проверка правил резерва оборудования |
| MT-000004 | На рассмотрении | Идея карты комплектации для ворот/шлагбаумов |
| MT-000005 | Нужно уточнение | Вопрос по комплектности возвращённого домофона |
| MT-000006 | В работе, просрочено | Фильтр просрочек и изменение срока с причиной |
| MT-000007 | В работе | Активный эксперимент с ярлыками блоков питания |
| MT-000008 | Ожидает подтверждения | Завершённый эксперимент, измерения и оценка автора |
| MT-000009 | Ожидает подтверждения | Подтверждение исправленной накладной на кабель |
| MT-000010 | Закрыто | Результат и сохранённое подтверждение автора |
| MT-000011 | Отклонено | Объяснение, почему нельзя автоматически снимать все резервы |
| MT-000012 | В работе после возврата | Предыдущее решение, отзыв автора и продолжение работы |
| MT-000013 | Получено | Собственное обращение ответственного об освещении |

У сотрудника 11 собственных обращений; у координатора очередь из 13;
у ответственного 10 назначенных и одно собственное. Чужие обращения
сотруднику недоступны. Просрочки/ожидание подтверждения рассчитаны относительно
времени загрузки: даты могут стать неактуальными после длительного хранения.

## Показ за несколько минут

Используйте отдельные профили/браузеры для разных ролей: вкладки одного
профиля разделяют cookie и не держат три независимых входа.

1. Координатор: очередь, неназначенные, просрочка MT-000006; назначить MT-000001.
2. Ответственный: назначенные обращения, вопрос MT-000005,
   активный эксперимент MT-000007 и завершённый MT-000008.
3. Сотрудник: ответить на уточнение MT-000005; подтвердить результат MT-000009.
4. При наличии времени: MT-000012 показывает, что отрицательная оценка
   действительно возвращает работу; MT-000010 — закрытие по подтверждению автора.

Действия на показе изменят состояние записей обычным способом. Скрипт не
сбрасывает такие изменения и не перезаписывает существующие обращения.

## Загрузка и проверка

Перед загрузкой сделан штатный backup БД и вложений; копия сохранена на
компьютере в `backups/vps/20261109T101958Z-FRaAAO.tar`.

```bash
# Из /opt/irontech после копирования файла скрипта и manifest:
./deploy/compose.sh cp deploy/seed_showcase.py backend:/tmp/seed_showcase.py
./deploy/compose.sh exec -T -e PYTHONPATH=/app backend python /tmp/seed_showcase.py < deploy/showcase-appeals.json
./deploy/compose.sh exec -T -e PYTHONPATH=/app backend python /tmp/seed_showcase.py --apply < deploy/showcase-appeals.json
```

Все записи создаются одной транзакцией с блокировкой и стабильными UUID.
Повторный запуск не добавляет дубликаты; частичный набор требует ручной
проверки. Автоматического удаления/сброса существующих данных нет.
Исторические уведомления доступны внутри приложения; их внешняя отправка
подавлена через существующий счётчик попыток доставки. Для просрочки заранее
созданы уведомления с обычным dedupe-ключом, чтобы worker не рассылал их повторно.
Новые действия пользователей обрабатываются обычными механизмами приложения.

Проверены HTTPS-вход/выход всех трёх аккаунтов, семь статусов, количество
и доступность обращений, фильтры неназначенных/просроченных/ожидающих
подтверждения, уточнение, эксперименты и обратная связь. Проверки выполнялись
чтением; подготовленные состояния сохранены для живого показа.
